## P0 — 上线前必须处理

### P0-1 失败记录会挡住同一篇稿子的重试（功能性阻断）

- **证据**：`server/app/routes/records.py:186` 判重查询只过滤 `is_deleted=False`，不区分 `status`；
  `server/app/models.py:118` 的唯一索引同样不含 status。
- **现象**：PS 没开 / 模板打开超时 → 写入一条 `failed` 记录 → 员工修好 PS 再点生成同一篇稿
  → 服务端返回 409「你今天已经用这个模板录入过同一作者+标题，请勿重复提交」。
  员工只能改标题造假或等管理员删记录。
- **为什么现在没暴露**：现有 185 个用例没有一条覆盖「失败后重试同一篇」。
- **修法**：唯一索引改为仅约束成功记录
  `CREATE UNIQUE INDEX ... WHERE is_deleted = 0 AND status = 'success'`，
  判重查询同步加 `status == STATUS_SUCCESS`；把旧索引名加进
  `server/app/migrations.py:_DEPRECATED_INDEXES` 让老库自动切换。
- **验收**：先提交 failed 再提交同键 success → 201；两次 success → 409。

### P0-2 依赖未锁版本

- **证据**：`requirements.txt` 全是 `>=`。
- **风险**：NAS 上 `docker compose build` 随时拉到新版 SQLAlchemy / Flask，跨大版本一次白屏，
  而你手里没有「上次能跑的版本」。
- **修法**：`pip freeze > requirements.lock.txt`，Dockerfile 优先装 lock；或直接改成 `==`。

### P0-3 成品图没有备份，且备份与库同盘

- **证据**：`server/backup.py` 只对 `app.db` 做热备；`server/backup.py` 的 BACKUP_DIR 在
  `server/data/backups`，与 `images/` 同一块盘。
- **风险**：单盘故障 = 190 张成品图全丢，只剩数据库里的路径。
- **修法（择一）**：① NAS 存储空间开定时快照（最省事，绿联自带）；
  ② cron `rsync -a data/images/ /volume2/backup/images/`；
  ③ 备份脚本增加图片月度打包。

### P0-4 容器日志无上限

- **证据**：`docker-compose.yml` / `deploy/nas/docker-compose.yml` 无 `logging` 段。
- **风险**：json-file 驱动默认无限增长。NAS 系统盘写满会连带其它容器一起挂。
- **修法**：
  ```yaml
  logging:
    driver: json-file
    options: { max-size: "10m", max-file: "3" }
  ```

### P0-5 静默失败没有任何外部告警

- **证据**：`bot/scheduler.py:backup_job` 异常只 `logger.exception`；日报推送失败只在后台徽标体现；
  磁盘占用只在仪表盘展示。
- **修法**：复用现成的 `bot.report.push_alert()`，在这三处推群：
  ① 备份失败；② 定时日报推送最终失败；③ 图片目录超过阈值（如 20 GB）。
  另加外部探针（Uptime Kuma / NAS 自带监控）盯 `/health/ready`，NAS 整机宕机也能知道。

## P1 — 已决策不做：模板 / 合作伙伴留在客户端

> 结论：**后台只负责查看数据**，模板 PSD 与合作伙伴名单继续由员工客户端上传/维护。
> 本节保留原始分析作为决策记录，代码未按此实施。

原始提案（把模板、名单、姓名、占位符、命名规则收到服务端统一管理）技术上可行，
但会把一个"员工自助 + 主管看数"的轻量工具，变成需要维护主数据的中台。当前团队规模下
收益不抵复杂度，因此**不实施**。

代价（需要认下，不是忽略）：

| 现状 | 影响 | 缓解方式（已落地或人工约定） |
|---|---|---|
| 模板在每台机器 | 模板改版要逐台通知/拷贝 | 模板目录可用共享盘；或统一放 NAS 共享路径指向 |
| 名单各机器独立 | 同一伙伴拼写不同会让报表分组分裂 | 约定"名单由一人定稿后分发"；后台可按关键词搜索合并看 |
| 姓名是自由文本 | 「李四」「李 四」在统计里是两个人 | 后台「员工」下拉来自记录，发现分裂可让当事人统一改名 |

若以后真出现"10 台以上机器、模板月更"的场景，再回到这一节按原方案做。

## P3 — 我补充的、你可能没想到的细节

1. **姓名是自由文本，没有员工管理页** → 统计按姓名分组，错一个字就是两个人。
   P1 的 employees 表顺带解决，客户端改下拉只读。
2. **失败的记录没有日志摘要** → 员工说「生不出来」，你只能让他去 `%APPDATA%` 找日志。
   失败上报时附 `worker.log` 最后 50 行（截断 500 字），直接进 `records.error_message`。
3. **没有「导出诊断包」按钮** → 建议加一个：打包 logs + config + 最近 3 个 task 的 status.json 成一个 zip，
   员工一键发你。（`/status` 已经返回 `log_dir`，接上即可）
4. **没有版本兼容校验** → 服务端改判重规则 / 加字段后，老客户端静默出错。
   `/health` 返回 `min_client_version`，客户端启动比对并提示升级。
5. **没有自动更新** → 每次发版逐台重装。Tauri 2 自带 updater，配一个静态目录即可，半天工作量。
6. **首次配置全靠手填** → 服务器地址打错一个字符就是「连不上」，是最高频的安装事故。
   安装包内置默认 `server_url`，或后台生成一段「配置串」让员工粘贴。
7. **软删除的图片永久保留**（`storage.py:96` 只在并发失败时删）→ 两年后 `images/` 几十万文件，
   NAS 上列目录都卡。加「按月归档到 cold/」任务。
8. **TIF/PSD 上传没有缩略图**（`storage.py:78` 只处理 jpg/png）→ 列表回退加载原图，一页 20 张能卡死。
   要么禁止非 jpg 上传，要么用 Pillow 生成。
9. **图片落盘与入库不在同一事务** → commit 非 IntegrityError 失败（如磁盘满）会留下孤儿文件。
   加一个每周对账任务：扫 `images/` 与库比对，孤儿文件进 `orphan/`。
10. **审计日志只增不删** → 没有保留策略，一两年后单表几十万行。加「保留 180 天」清理。
11. **NAS 容器以 root 运行 + `chmod 777`**（`deploy/nas/docker-compose.yml`）→ 能跑但把权限问题永久掩盖。
    改用 `PUID/PGID` 环境变量 + 一次性 `chown`。
12. **CI 只跑 pytest**（`.github/workflows/tests.yml`）→ `vue-tsc`、`vitest`、`vite build` 全不在流水线里，
    前端改崩了 CI 依然绿。加一个 `client` job（node 20，三条命令）。
13. **单测覆盖率盲区**：没有「失败后重试」「空库首次启动」「图片缺失」这三类用例，而它们都是真实踩过的坑。
14. **`client_machine` 用 `platform.node()`** → 员工改过电脑名就是两条不同机器，排障时误导。
    改成「机器名 + 登录用户名」或干脆用 MAC 哈希。

## 第四轮：主窗去掉死白（同日更晚）

用户看完第三轮的截图，第一句话是"为什么看着这么多的空白地方，也没啥用"。
问题出在第三轮自己的解法上：我把 380 高的窗口里那 140px 空白当成"排版问题"，
用 `margin:auto 0` 把表单垂直居中，上下各摊 70px 对称留白——**空白一点没少，
只是从"堆在下面"变成"上下各一半"，还更难解释**。真正的错是把窗口高度写死了。

改法：高度不写死，交给内容决定。

| 项 | 改前 | 改后 |
|---|---|---|
| 窗口高度 | 固定 380（配置写死） | 初始 222，运行期由内容决定：常态 **222**、带配置提示条 **~280**、带结果条 **~311** |
| 死白占比 | 140px / 37% | 0（`body.scrollHeight == clientHeight`） |
| 垂直定位 | `margin: auto 0` 上下均分空白 | 顶部对齐，`margin: 0` |

实现分三层，缺一层都会退化成"抖"或者"抢用户"：

1. **量**（`App.vue` 的 `naturalMainHeight`）。`.stack` 是 `flex:1 0 auto` 会被撑满，
   它的 `scrollHeight` 只是"当前高度"，必须递归进它的孩子才是内容真实高度；
   `.form-body` 这类不拉伸的块直接用 `scrollHeight`。最后加上头部与底栏。
2. **改**（Rust `set_main_height`）。只换算逻辑像素、只改高度不动宽度——
   `inner_size` 是物理像素，除 `scale_factor` 才是逻辑宽度，否则高 DPI 下横向会被拉长。
3. **触发与收敛**。`ResizeObserver` 盯 `.form-body / .setup-strip / .result`，
   `MutationObserver` 盯节点增删；加**滞回**：装不下立刻长高，装得下且富余 ≥6px 才缩。
   没有滞回会来回抽：滚动条出现 → 可用宽度少 7px → 文字换行 → 自然高度变大 →
   缩回去 → 滚动条消失……窗口底边一直抽搐。

还有一个必须留的"让位"：员工手动把窗口拖高了（`innerHeight` 与我们设的值差 >12px）
就把 `autoFit` 关掉，本进程内不再改高度。否则他拖大一点，下次生成完又被弹回原位。

顺带把 `minHeight` 从 320 降到 180（否则 Rust 那边的尺寸夹紧会让自适应失效），
`svg`/配置初始高度统一到 222（= 实测自然高度 +1，`+1` 是为了亚像素取整后不冒滚动条）。

`scripts/measure_layout.js` 也跟着升级：现在会打印"自适应高度 = Npx，
窗口 W → 死白 (W-N)px 占 X%"，改完直接看这个数就知道有没有白留。

回归：`cargo check` 通过；`vue-tsc --noEmit` 通过；`pytest -q` 209 passed；
重截 `w-main` 确认底部只剩 10px 内边距、无滚动条；注入「配置提示条 + 结果条」
验证自然高度会从 221 长到 311。

## 第六轮：贴边方向不该由设置决定（用户提问）

用户原话：「贴边方向不应该设置里设置，不应该是自动的吗，就像QQ隐藏一样。」
说得对——**贴哪一边是运行时才知道的事**：窗口停在哪条屏缘附近就该贴哪条，
提前在设置里选一遍，选错了还得回去改。原来的实现也确实有这毛病：
设置里给「不贴边/贴左缘/贴右缘/贴上缘」四个胶囊，员工还得先理解这个选项。

### 改法

| 项 | 改前 | 改后 |
|---|---|---|
| 设置窗「外观」 | 贴边方向 4 个胶囊 + 自动贴边开关 | 只有「拖到边缘自动贴边」总开关，hint 明说**贴哪边看离哪边近，不用选** |
| 主窗贴边按钮 | 读 `config.dock_side`，没有就默认 `right` | 调 `dock_main_nearest`，Rust 按窗口中心到三边距离挑 |
| 拖到屏缘 24px 内 | `check_auto_dock` 挑最近的一缘 | 不变（本来就是 QQ 的做法，之前缺的只是"设置里多此一举"） |
| `dock_side` 字段 | 员工可设的偏好 | 纯运行状态："上次贴到哪边"，用于下次启动还原，界面不展示 |

三个容易漏的点：

1. **贴上时也要广播**。原来只有取消贴边才发 `dock-changed{side:null}`，
   贴上前端拿不到是哪一边，`dock_side` 就没法落盘、重启后不还原。
   现在 `dock_window` 一并广播 `{side}`，前端统一在 `listenDockChanged` 里
   记状态 + 落盘，`toggleDock` 不再自己摸 `docked`。
2. **底部永远不是候选**。按距离挑边时若把底边算进去，任务栏会被压住。
3. **等距时要确定**。左右等距不能随遍历顺序变，fold 里用 `<=` 保住先出现的那条。
   顺带一提：屏幕正中时会贴到**上缘**（距上 540 < 距左 900），比贴左右更不挡同事。

### 测试

纯函数 `nearest_side(cx, cy, mpos, msize)` 从 Tauri 命令里抽出来单独测（这玩意
跑起来需要真窗口）：4 个用例——三边各自最近、屏幕正中、等距确定、副屏坐标偏移
（副屏原点 x=1920）、底部永不入选。`cargo test` 4 passed。

`pytest` 210 passed；`vite build` 通过。设置窗「外观」标签重截确认方向项已消失。

## 第七轮：Photoshop 路径自动识别（用户提问）

用户原话：「PS路径不应该是自动识别吗，任意ps版本」。

先查了一遍现状，结论是**路径本来就没被真正用上**：`PSConnector.connect(photoshop_exe)`
收了参数却一次都没看，连接走的是版本无关的 ProgID
`win32com.client.Dispatch("Photoshop.Application")`——所以"任意版本能连"早就成立，
CS6 和 2025 一样连。路径只在两处有用：读 exe 的文件版本写进记录
（`_ps_version`）、以及在设置里展示。就为这两件事让员工记住
"Adobe Photoshop 2024" 装到哪个盘，是一道白花的门槛。

### 识别顺序（都找不到才轮到手动填）

1. 设置里手填的路径 —— 员工明确指定时以他为准
2. **注册表 `App Paths\Photoshop.exe`** —— Adobe 自己注册的"默认 PS"，
   CS6 / CC / 2020+ 全都有，且不受装在哪个盘影响
3. 卸载信息里的 `InstallLocation`（DisplayName 含 Adobe Photoshop，
   排除 Elements：另一款软件，没有 `Photoshop.Application` COM）
4. 常见安装目录扫描 —— 兜底，给手工挪过目录、注册表被清理过的机器

多候选时取**版本最高**：COM 的 ProgID 解析到的通常也是最新版，两者一致，
员工才看得出连的是同一个。

**本机实测证据**（这台开发机装的是 CS6、在 D 盘）：

```
App Paths  → D:/Program Files\Adobe\Adobe Photoshop CS6 (64 Bit)\Photoshop.exe  13.0.0
uninstall  → D:/Program Files\Adobe\Photoshop.exe
scan       → D:/Program Files\Adobe\Adobe Photoshop CS6\Photoshop.exe
识别结果   → app-paths / 13.0.0
```

只扫 `C:/Program Files\Adobe` 的话，这台机器一个都找不到——这正是"任意盘符"
必须靠注册表而不是目录扫描的原因。

### 顺手修掉的三处

1. **`ps_version` 以前永远写不进去**。`fields["ps_version"] = _ps_version(cfg.ps_path)`，
   而 `ps_path` 默认空 → 记录里这一列常年是空，报障时问"你装的哪版"还得再问一遍。
   现在用识别出的版本。
2. **传给 worker 的 ps_path 以前是空串**，日志里看不出连的是哪个 PS。现在传识别出的真实路径。
3. **手填路径失效时不再装死**：自动识别顶上（生成不该被一个过期的手填值卡住），
   同时 `override_missing` 把真相带回界面——"你填的路径不存在，当前用的是自动识别结果"。
   静默回退会让员工以为填对了，然后生成时连的是另一个 PS。

### 界面

- 设置窗「高级」：Photoshop 路径从"必填感的文本框"变成**留空＝自动识别（推荐）**，
  下面一行状态显示「已自动识别 版本 13.0.0 + 路径 + 来源 + 重新识别按钮」。
  路径很长，单独一行 `word-break: break-all`，不撑宽窗口。
- 「重新识别」装完/换版本后点一下即可，不用重启软件；结果立刻显示
  （本地 `psLocal` 覆盖 props，否则要等最多 60 秒的下一次轮询）。
- 主窗加一条提示卡：**没识别到 Photoshop 就在这儿说**，别等员工点完生成
  才弹一个看不懂的 COM 错误。`com_available`（pywin32）那条更根本，优先报。

### 测试

`tests/test_ps_detect.py` 14 个用例：纯函数（年份解析、exe 判定、排序键）、
挑最优（文件版本优先/读不到时按目录名/全不存在）、识别顺序三级回落、
手填优先且不碰系统探测、手填失效的两种结局、`to_dict` 形状。
探测函数通过 `detect_with()` 注入假候选，**不需要真装 PS**。
